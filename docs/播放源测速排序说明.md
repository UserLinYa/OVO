# 增量抓取与测速管道设计

本文件补充 README 的实现细节，面向需要改代码/调参数的维护者。

## 1. 数据流

```text
Demo.txt ─┐
sources/*  ─┼─> ParseBundle ─> canonicalize_sources ─> StateManager.library
remote     ─┤                        │                       │
zubo scan  ─┘                        │                       ▼
                                     │              build_probe_plan
                                     │                       │
                                     │              ProbeRunner (cache-aware)
                                     │                       │
                                     └────────────> apply_probe_results
                                                             │
                                                      select_channels
                                                             │
                                                      write_outputs
```

`apply_probe_results` 会把探测得到的**原始流畅度指标**（中位速率、抖动、停顿、
声明码率、分片时长、成功 EWMA）写进 `library.json`；评分本身不落盘，由
`itvpipe/smooth.py` 按当前 `[ranking]` 配置实时计算，所以调权重不需要重新测速。

## 2. 增量状态

| 文件 | 内容 | 作用 |
| --- | --- | --- |
| `state/probe_cache.json` | canonical URL → 最近测速结果 | TTL 内不再请求 |
| `state/library.json` | 频道 → URL → 健康记录/历史指标 | 抓取失败时保留上一轮可用源 |
| `state/run_state.json` | 上次运行、上次酒店扫描 | 扫描节流 |
| `state/output_hashes.json` | 输出文件 SHA-256 | 内容不变不重写 |

`SourceRecord` 同时保留 `last_ok_at`、`fail_count`、`quarantined_until`。失败源不会立即删库，而是先退出输出、退避、再隔离，避免一次网络抖动把好源永久删掉。

`state` 版本为 2。旧文件缺失的新字段按“未测量”处理：`kbps_p50=None`、`stalls=0`、
`success_ewma=0`，评分自动退回 `kbps` + 中性可靠性，无需迁移脚本。建议升级后跑一次
`--force-probe`，让所有源都拿到流畅度指标。

## 3. 测速预算

1. 先按 `(频道, URL)` 合并抓取结果。
2. 每频道按“已缓存可用数”计算配额：
   `quota = max(0, target - healthy) + max_new_per_channel`；
3. 候选按“待复测的已知好源 → 新源 → 隔离到期的失败源”排序；
4. 全局按轮次分配（round-robin），没有可用源的频道优先；
5. 去重后交给 `ProbeRunner`，同一 URL 只测一次；
6. 实际请求量受 `max_probes_per_run` 硬限制。

采样量比旧版大：`sample_bytes` 默认 384 KB、`sample_seconds` 默认 3s，按 16 KB
窗口读取。窗口数直接决定抖动/停顿统计有没有意义——128 KB 只能拿到两个窗口，
算不出分布。

## 4. 缓存键

使用 `canonical_url()` 的规范化结果：

- scheme/host 小写；
- 去掉默认端口、fragment；
- 去掉 `utm_*`/`spm`；
- 不对业务 query 排序（签名 URL 不能被重排）；
- 播放地址保留原始 query。

## 5. 失效清理

- 探测失败：`fail_count += 1`，状态改为 `failed`，立刻退出输出；
- 达到 `drop_after_failures`：写 `quarantined_until`，期间不再请求；
- 隔离到期：允许重新探测；
- 长期无活动：`state.prune()` 按 `retain_hours` 删除记录；
- 连续失败清理只影响该 URL，同频道其他源仍可用。

## 6. 输出哈希

`OutputTracker` 保存每个输出文件的内容 SHA-256。`write_if_changed()` 先比较哈希，再决定是否 `os.replace()` 原子写入。GitHub Actions 的提交步骤只看 `git diff`，因此没有内容变化时不会产生提交。

TXT 的“更新时间”来自所选源最近的 `last_ok_at`；缓存命中时保持稳定，不会每轮都产生仅时间不同的 diff。

完整 M3U/TXT 末尾会追加一个 `更新时间` 分组，条目为 `时间戳,http://123.MP4`（M3U 使用同样的时间戳作为条目名）。该行为由 `output.append_update_entry` / `output.update_entry_url` 控制；拆分后的 `dist/groups/` 文件不重复追加。

## 7. 流畅度评分（替代“测速最快”排序）

### 7.1 为什么换

旧实现把一次 128 KB 短突发的峰值速率当作主要排序键：

```python
rank_key = (tier, -kbps, latency_ms, quality, -priority)
```

问题在于峰值 ≈ 起步那几百毫秒的 TCP 窗口，和“能不能连续播下去”几乎无关：

- 抖动大 / 限速式滴流的源，峰值可以很高，播放几十秒就开始重缓冲；
- 首帧慢的源换台要等，但峰值高仍然排在前面；
- 历史上一半轮次失败的源，只要这一次测出高速度，仍然会被推到第一位；
- 128 KB 只有两个 64 KB 读窗口，连分布都算不出来。

### 7.2 怎么算

`itvpipe/probe.py` 逐窗口记录 `(到达时刻, 本次字节数)`；`itvpipe/smooth.py`
的 `analyze_samples()` 把它们换算成：

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| `kbps` | 总字节 / 总时长 | 报告里的“平均码率”，保留兼容 |
| `kbps_p50` | 把时间轴重采样成固定桶（`3×常态间隔`，夹在 0.1~0.5s）后，桶速率的 50 分位 | **排序用的有效速率**，抗突发 |
| `kbps_p25` | 桶速率的 25 分位 | 最差窗口的参考值 |
| `jitter` | 桶速率的变异系数 | 稳定性分量 |
| `stalls` | 原始读取间隔 ≥ `max(stall_seconds, 3×p25间隔)` 的次数 | 停顿分量 |

另外 `ProbeResult.retries` 记录这次成功前重试了几次：连接被重置/读取不完整本身就是
抖动信号，重试成功只按半次成功计入可靠性。

评分（`smoothness_score()`）：

```text
speed       = min(持续码率 / 需求码率, 1.2) / 1.2
stability   = 1 / (1 + jitter_scale * jitter)
stall       = 1 / (1 + stalls)
latency     = 1 / (1 + 首帧秒数)
reliability = 成功次数 EWMA（新源 0.7，成功 +0.35，失败 -0.6，重试后才成功按半次）

base  = 100 * Σ(权重 × 分量)              # 权重默认 0.34/0.30/0.16/0.08/0.12
feasible = min(1, 需求比例 / min_adequacy) # min_adequacy 默认 0.8
score = base * (shortfall_floor + (1 - shortfall_floor) * feasible)
```

“需求码率”取三者最严：

1. HLS 主列表里选中变体的 `BANDWIDTH`（播放器实际按它消耗）；
2. 媒体列表的 `EXT-X-BITRATE`；
3. 清晰度兜底表（1080p→4000 kbps 等，可由 `ranking.required_kbps` 覆盖）。

如果拿到了分片大小（`Content-Length` / `Content-Range`）和 `EXTINF` 时长，
还会算“能否在播放消耗完之前下完一个分片”，跟不上就进一步压低 `speed`。

可行性系数的意义：码率不够的源再平稳也必然重缓冲，不能让它在加权和里靠
稳定性拿到中上游分数。

### 7.3 排序键

```python
(tier,                              # 0 实测 / 1 仅可达 / 2 失败
 -bucket_score(score, bucket),      # 流畅度分档，bucket 默认 1 分
 -round(effective_kbps),            # 同档内余量多的优先
 round(latency_ms / 100),           # 再按首帧（100ms 分档）
 -quality_rank(quality),
 -priority)
```

`select_channels` 还会追加 `canonical_url` 作为最终 tie-break，保证完全相同的输入
产生完全相同的顺序。分档 + URL 兜底是为了**抑制输出抖动**：测量噪声导致的微小
分数变化不会让播放列表每轮换位，从而避免无意义的 commit。

`[ranking] mode = "speed"` 时回到旧键 `(tier, -kbps, latency, quality, priority)`，
方便对比或回滚。

### 7.4 调参建议

| 现象 | 调整 |
| --- | --- |
| 播放列表换源太频繁 | 调大 `ranking.score_bucket`（如 3~5） |
| 太看重速度，抖动源仍排前 | 调高 `w_stability` / `w_stall`，或调大 `jitter_scale` |
| 低码率源被淘汰得太狠 | 调低 `min_adequacy`（如 0.6）或调高 `shortfall_floor` |
| 清晰度需求估计不准 | 覆盖 `ranking.required_kbps` |
| 干脆想要旧行为 | `ranking.mode = "speed"` |
